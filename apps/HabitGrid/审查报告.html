二、需要修复的问题

中 · 功能性 Bug删除习惯后 Widget 残留

ViewModels/HabitViewModel.swift:130 delete(_:)

delete() 只调用了 save()，没有调用 WidgetDataBridge.sync。 打卡（saveAndSync）、新建/编辑（在 HabitFormView 里补了 sync）都会刷新小组件，唯独删除不会—— 被删的习惯会在主屏小组件里一直残留，直到下一次任意打卡或冷启动 App 才消失。

这同时违反了 CLAUDE.md 的明文约定：「业务写操作集中在 HabitViewModel，写库后调用 WidgetDataBridge.sync」。

修复：在 delete() 的 save() 之后追加一行 WidgetDataBridge.sync(from: context)（与 saveAndSync 同款）。

低 · 一致性Widget 同步逻辑分散，未真正「集中在 ViewModel」

HabitViewModel.swift（createHabit/update/delete/persistOrder） vs HabitFormView.swift:223

当前 sync 调用散落三处：打卡在 VM 内，新建/编辑靠 View 层 HabitFormView.save() 补救，删除/排序则完全缺失。 与设计约定不符，且容易在后续新增写路径时再次漏同步（Bug #1 正是这样产生的）。

建议：把 WidgetDataBridge.sync 统一收敛到 VM 的 createHabit / update / delete / persistOrder 内部，移除 View 层的那次调用，形成单一约束点。

低 · 死代码persistOrder 从未被调用

HabitViewModel.swift:137 · ContentView 的 ForEach 无 .onMove

排序 API 已实现但列表没有任何重排序入口，sortOrder 实际永远等于创建顺序。 要么补上拖拽重排 UI（.onMove + 同步），要么按「精准改动」原则暂时保留并标注 TODO（不建议本次删除）。

低 · 性能当前连续天数计算存在 O(n²)

Utils/HabitStatistics.swift:112 currentStreak

回溯 while 循环里每次迭代都重算一遍 completedDays.min()。数据量小时无感，但属无谓开销。

修复：把 let earliest = completedDays.min() 提到循环外计算一次。

低 · 上架细节通知用了 .timeSensitive 但未声明对应能力

Utils/NotificationManager.swift:66 · HabitGrid.entitlements

content.interruptionLevel = .timeSensitive 需要 Time Sensitive Notifications 能力。 entitlements 未声明 com.apple.developer.usernotifications.time-sensitive，系统会静默降级为普通通知——不报错，但达不到「专注模式下也提醒」的预期效果。

修复：在 Xcode 为主 Target 添加该能力；否则把级别降为 .active 以免误导。

低 · 潜在地雷CloudKit 开关与 @Attribute(.unique) 不兼容

Models/Habit.swift:50 · HabitGridApp.swift:29 注释

入口注释写着「如需 CloudKit 改为 .automatic」，但 Habit.id 用了 @Attribute(.unique)，而 CloudKit 不支持唯一约束。谁照注释一改就会运行时崩溃。 当前默认 .none 安全，但这是个埋给未来自己的坑。

建议：把注释改为明确警告，或预先去掉 .unique（靠 UUID 天然唯一）以便随时启用同步。

低 · 健壮性每日唯一性仅靠应用层保证

Models/HabitEntry.swift · 无 (habit, day) 复合唯一约束

「每习惯每天一条」全靠 entries.first(where:) 在写前查重。当前所有写操作都在 @MainActor 单线程，安全；但缺数据库级兜底，未来若引入后台导入/同步易产生重复日键。属可接受的现状风险，记录备查。

低 · 细节次要不一致与 cosmetic

  • 默认值不一致：Habit.weeklyTarget 默认 7，HabitFormView 默认 5（无功能影响，建议统一）。
  • 成功触感偏频繁：toggleCheckIn 中 currentStreak == longestStreak 在首次打卡及每次平/刷新纪录时都会触发 Haptics.success()，体感上可能略密。
  • 周首硬编码：热力图固定周日为周首（GitHub 风格，符合设计），但 thisWeekCount「本周」对周一为周首的地区语义略偏；建议加注释说明是有意为之。

三、值得肯定的地方

优秀Swift 6 严格并发处理到位

所有有状态管理类（PurchaseManager / NotificationManager / HabitViewModel）均 @MainActor 隔离； listenForTransactions 用普通 Task 继承隔离而非 detached、并用 [weak self] 避免捕获非 Sendable 的 self——细节正确，看得出对并发模型有理解。

优秀StoreKit 2 流程完整且经得起边界

购买的 success / userCancelled / pending / 未验证(checkVerified) / 撤销(revocationDate) 分支全覆盖； 本地 UserDefaults 缓存 isPro 保证离线与启动瞬间 UI 即时正确；currentEntitlements 重算授权。付费墙、主题锁、3 个习惯免费上限形成闭环。

优秀统计逻辑纯函数化、可测试、防御充分

HabitStatistics 与 SwiftData 完全解耦，输入纯日期集合；连续/最长/完成率/本周计数分别独立； 回溯循环都设了 4000/8000 的安全上限防坏数据死循环。「今天没打卡不惩罚连续」的处理符合产品直觉。

优秀本地化与上架合规

中/英两份 Localizable.strings 键集完全对齐（逐条核对，含全部 %lld / %@ 占位）； 隐私政策 App 内可离线访问、条款指向 Apple 标准 EULA、ITSAppUsesNonExemptEncryption=false 已声明、健康分类正确——上架要素齐备。

优秀组件复用与架构清晰

HeatmapView 不持有数据、只收 intensity 闭包 + palette，在列表行/详情/导出卡三处复用； 每个习惯用自身颜色经 Color.heatLevels 在 HSB 空间生成同色系四级深浅，实现正确； Widget 经 App Group 快照解耦 SwiftData、次日 0 点刷新 timeline，边界考虑周到。
