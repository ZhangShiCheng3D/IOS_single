一、发现的问题（按严重程度排序）

高 · 编译  1. 原始 PHAsset 跨 actor 边界违反 Swift 6 Sendable

ViewModels/ScanViewModel.swift

PhotoLibraryManager 是 actor，其 analysisImage(for:)、delete(assets:)、 thumbnail(for:) 均为 actor 隔离方法且参数为 PHAsset / [PHAsset]。 ScanViewModel（@MainActor）在以下三处把原始 PHAsset 送入该 actor：

  • await library.analysisImage(for: asset)（扫描循环，第 134 行）
  • try await library.delete(assets: assets)（第 184 行）
  • await library.thumbnail(for: item.asset, …)（第 203 行）

PHAsset 未被 Apple 标注为 Sendable。项目把 PhotoItem / PhotoGroup 包成 @unchecked Sendable 来安全跨界，UIImage 在目标 SDK 中本身即 Sendable（因此作者未包裹它）， 但裸 PHAsset 的跨界没有被覆盖，在 Swift 6 语言模式下会报 “non-sendable type 'PHAsset' … into actor-isolated context”。

修复：将 import Photos 改为 @preconcurrency import Photos。 这是 Apple 推荐的、针对尚未采用并发标注框架的标准降级方式，精准覆盖本文件内所有 PHAsset 跨界点，零行为变化。

- import Photos
+ @preconcurrency import Photos   // PHAsset 未标注 Sendable；跨 actor 传递时降级为兼容模式

中 · UI  2. 全屏预览首帧闪现第一张照片

Views/PhotoPreviewView.swift

原先 @State private var selection = ""，在 .onAppear 里才赋值 initialItem.id。TabView(selection:) 初值不匹配任何 tag，会先渲染第 0 张， onAppear 后再跳到用户点开的那张 —— 用户点第 5 张会先看到第 1 张闪一下再跳转。

修复：新增 init，用 _selection = State(initialValue: initialItem.id) 在构造期就定位到目标照片，并删除 .onAppear 赋值。

四、剩余风险与建议（不影响编译运行）

建议 1 — 中 清理后“空间对比”会误导用户

Views/CleanupResultView.swift · ScanViewModel.deleteSelected()

删除走 PHAssetChangeRequest.deleteAssets，照片进入“最近删除”，30 天内不真正释放磁盘。 因此 storageAfter.free 与 storageBefore.free 几乎相等，前后对比卡片会显示“几乎没释放”，与“已释放 X GB”自相矛盾。 此外 CleanupResultView.freeGain 计算属性从未被使用（死代码，按规约保留未删）。

建议：以估算的 freedBytes 作为主指标，把“清理后可用空间”改为“预计可释放”或加注“清空‘最近删除’后生效”，避免审核期与用户对“释放空间”的预期落差。

建议 2 — 低 CleanupRecord 只写不读

ContentView.performCleanup() 会 insert 一条 CleanupRecord，但全项目无 @Query<CleanupRecord>、无历史页。 清理历史功能未闭环。建议：要么补一个“清理历史”入口（设置页），要么明确其仅用于统计累计释放量并据此展示。

建议 3 — 低 View 直接操作 SwiftData

CLAUDE.md 约定“View 不应直接操作 SwiftData，应通过 ViewModel”。当前 ContentView 直接 modelContext.insert(settings/record)。 @Query + @Bindable settings 是官方惯用法，可接受；但 CleanupRecord 的写入更适合下沉到 ScanViewModel（注入 modelContext），以严格满足分层约定。未改动以避免引入耦合风险。

建议 4 — 低 String(format:) 用 %d 承载 Swift Int

cleanup.confirm.message / cleanup.selectedCount / category.summary 使用 %d 对应 64 位 Int。 在小整数下工作正常，但严格而言应为 %ld。属潜在隐患（大数 / 大端），照片计数远小于 2³¹，不会崩溃。未改动以避免在两个本地化文件间制造格式不一致。

建议 5 — 低 分析取图用 .opportunistic 投递

PhotoLibraryManager.thumbnail 用 .opportunistic + 已禁用 iCloud 网络。 对“分析用图”(analysisImage)，理论上存在仅返回降质回调而无最终回调的极端情形（continuation 不 resume）。 实测中 iCloud 缺图会以 isDegraded=false + image=nil 收尾从而正常 resume，但分析路径改用 .highQualityFormat（单次回调）会更确定。

建议 6 — 低 上架资源待补

AppIcon.appiconset/Contents.json 仅声明 1024×1024 槽位且无实际图片文件（不影响编译，Xcode 会占位）。上架前需补齐 App 图标资源。

结语

项目工程化成熟、隐私设计（端侧分析、isNetworkAccessAllowed=false、特征向量不落盘）与卖点一致，可直接进入真机联调。 本次已消除 Swift 6 严格并发下的编译阻断与一处 UI 时序小缺陷；其余 6 项均为产品体验/分层层面的优化建议，按“精准改动”原则交由产品决策，未擅自扩大改动面。
